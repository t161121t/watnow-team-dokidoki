## 0. 前提: Prisma と Supabase の役割分担

`chore/setup-DB` で Prisma を導入した際、**実行時のDBアクセスもPrisma Clientで行う**方針を選んだ（Supabase Client の `.from()`/`.rpc()` は使わない）。

これは型安全性を優先した選択だが、副作用として重大な注意点がある:

> **Prisma Client は直結の Postgres 接続であり、何もしなければ RLS（Row Level Security）を素通りする。**

AGENTS.md はグループ完全分離を「RLS + Function内チェックの二重防御」で守ると定めている。Prisma を実行時に使う以上、この防御をアプリ側で意図的に再現する必要がある。それが §2 の `withRlsContext` の役割。

| 用途 | 使うもの | 理由 |
| --- | --- | --- |
| テーブルの read/write、PostgreSQL Function(RPC)呼び出し | **Prisma Client**（`lib/db/rls.ts` 経由） | 型安全。ただしRLSを自前で保証する必要がある（§2） |
| ログイン状態の確認（`auth.uid()` に相当する情報の取得） | **Supabase Client**（`lib/supabase/server.ts`） | Prismaは認証を持たない。Supabase Authのセッション/Cookieを読むだけ |
| ファイルアップロード・署名付きURL | **Supabase Client**（Storage） | Prismaの管轄外 |
| リアルタイム購読（価格更新など） | **Supabase Client**（Realtime） | Prismaの管轄外 |

**Supabase Client で `.from()` や `.rpc()` を呼ばない。** テーブルアクセスの経路を1本（Prisma）に統一しないと、RLSの保証漏れに気づきにくくなる。

## 1. レイヤー構成

```
app/                    Next.js App Router（ルーティング・レイアウトのみ）
features/<domain>/      ドメイン単位のUI・Server Actions・DBアクセス
  components/             このドメイン専用のUIコンポーネント
  actions.ts              Server Actions（認証確認 + 入力バリデーション + server/ 呼び出し）
  server/                  Prisma / RPC 呼び出し本体
  types.ts                 このドメインの型（任意）
components/              ドメインに依存しない汎用UIコンポーネント
lib/
  prisma.ts                Prisma Client シングルトン
  db/rls.ts                 RLSを効かせて Prisma を呼ぶための唯一の入口
  supabase/server.ts        Auth・Storage・Realtime専用のSupabase Client
prisma/
  schema.prisma            テーブル・カラム・enum・インデックス（Prisma Migrate管理）
  sql/<domain>/*.sql       PostgreSQL Functions・RLSポリシー・trigger（手書き。§3）
scripts/                  開発・運用用の単発スクリプト
```

ドメイン: `auth`（サインイン/サインアウト・オンボーディングのプロフィール作成）/ `groups`（グループ・招待）/ `secrets`（秘密・出品）/ `auctions`（オークション・入札・ディーラー）/ `wallet`（ポイント）/ `challenges`（ミニゲーム）。`auth`以外の境界は [`DB.md`](./DB.md) のテーブル区分と揃えている。

### 1.1 依存の向き（どのファイルが何をimportしてよいか）

```
app/
 ├─→ features/<domain>/components
 ├─→ features/<domain>/actions.ts
 ├─→ components/
 └─→ lib/（汎用のみ）

features/<domain>/components
 ├─→ features/<domain>/components（同じドメイン内のみ）
 ├─→ features/<domain>/server（同じドメインのみ。読み取り専用。§1.1a参照）
 ├─→ components/
 └─→ lib/（汎用のみ。lib/prisma・lib/supabase は禁止）

features/<domain>/actions.ts
 ├─→ features/<domain>/server（同じドメインのみ）
 ├─→ lib/supabase/server（ユーザーID取得のため）
 └─→ lib/（汎用）

features/<domain>/server
 ├─→ lib/db/rls.ts（withRlsContext 等。実クエリは必ずここ経由）
 └─→ lib/（汎用）
```

**ドメインをまたぐ import は禁止**（例: `features/auctions` から `features/wallet/server` を直接呼ばない）。落札確定のように複数ドメインにまたがる整合性が必要な処理は、アプリコードで2ドメインを跨いで呼ぶのではなく、**PostgreSQL Function側でまとめる**（`prisma/sql/auctions/finalize_auction.sql` が wallet・secrets 両方のテーブルを1トランザクションで更新する。AGENTS.mdの「複数テーブルの整合・入札・ポイント → PostgreSQL Function」という方針そのもの）。

#### 1.1a `features/<domain>/components` から `server/` を直接呼んでよい理由（2026-08-20方針変更）

`actions.ts`（`"use server"`）は本来、クライアント（ブラウザ）とサーバーの境界を越えるための仕組み。しかし Server Component（RSC）は最初からサーバー上でしか実行されないため、この境界越えの仕組みは読み取りには不要で、`components → actions.ts → server/` という経路は素通りするだけの層になっていた。

- **書き込みは今まで通り`actions.ts`を経由する**（認証確認 + Zodバリデーションの関所として機能させる）。`server/`は`captured`されたドメイン単位でのみ許可しているが、read/writeをESLintで機械的には区別できないため、「読み取りは直接、書き込みはactions.ts経由」はコードレビューで担保する規約とする
- `server/`は`import "server-only"`が付いているため、**Client Componentから直接importしようとするとビルドエラーになる**。つまりESLintのルールを緩めても、実際に`server/`を直接呼べるのはRSCだけで、Client Componentから素通しで書き込まれる心配はない
- `"use server"`でexportした関数（Server Action）は、呼び出し元をRSCだけに限定することはできない（action IDが分かれば理論上クライアントから直接叩ける）。つまり`actions.ts`経由にしたところで「クライアントから直接呼ばれない」保証にはならず、結局各Server Actionが自分で認証確認する必要がある（今の実装はそうなっている）。読み取り専用でクライアントから呼ぶ予定が無い関数を`actions.ts`に置く意味は薄い
- `server/`の関数は`userId`を明示的な引数として受け取る設計（`withRlsContext`が要求するため）。RSCから直接呼ぶ場合も、呼び出し側（RSCやその上位のlayout等）が`getCurrentUserId()`相当で取得したuserIdを渡す必要がある（暗黙の認証は無い）
- 将来、ある読み取りをClient Componentから呼ぶ必要が出てきた場合（例: 検索ボックスのライブ検索）は、その関数用に`actions.ts`へ薄いラッパーを追加すればよい（`server/`の実装はそのまま再利用できる）

## 2. `withRlsContext` の仕組み

`lib/db/rls.ts`:

```ts
export async function withRlsContext<T>(
  userId: string,
  fn: (tx: Prisma.TransactionClient) => Promise<T>,
): Promise<T> {
  return prisma.$transaction(async (tx) => {
    const claims = JSON.stringify({ sub: userId, role: "authenticated" });
    await tx.$executeRaw`SELECT set_config('request.jwt.claims', ${claims}, true)`;
    await tx.$executeRaw`SET LOCAL ROLE authenticated`;
    return fn(tx);
  });
}
```

やっていること:

1. `prisma.$transaction` でトランザクションを開始する（**必須**。`SET LOCAL` はトランザクション外では意味を持たない）
2. `request.jwt.claims` に `sub`（ユーザーID）をセットする。Supabaseが書く RLS ポリシーの `auth.uid()` はこの値を読む
3. `SET LOCAL ROLE authenticated` で、接続ロールを Prisma の特権ロールから `authenticated`（Supabaseが用意する、RLSが効く一般ロール）に一時的に切り替える
4. トランザクションが commit/rollback すると `SET LOCAL` も `set_config(..., true)` も自動的に元へ戻るので、コネクションプールの使い回しで権限が次のリクエストへ漏れることはない

これにより、`features/*/server/*` からのクエリは Supabase の RLS ポリシーに従う。**このラッパーを経由しない Prisma 呼び出しは特権ロールのままなので、RLSを素通りする** — だからこそ ESLint で `lib/prisma.ts` の直接 import を禁止している（§1.2）。

### 2.1 `withServiceRole`（例外）

cron から叩く `finalize_due_auctions` のように、特定ユーザーの代理ではなくシステムとして動く処理は `withServiceRole` を使う（RLSを意図的にバイパスする）。**通常のリクエスト処理からは使わない。** 新しく使う場合はPRで理由を説明すること。

## 3. `prisma/sql/`: PostgreSQL Functions・RLSポリシーの置き場

Prisma Migrate はテーブル・カラム・enum・インデックスは管理できるが、`CREATE FUNCTION` や `CREATE POLICY` のような Postgres 固有のSQLはスキーマ言語で表現できない（`prisma/schema.prisma`に書けない）。

そのため、この手書きSQL群は `prisma/sql/<domain>/*.sql` に分離し、`prisma migrate deploy` の後に別スクリプトで適用する:

```bash
npx prisma migrate deploy   # テーブル定義（schema.prisma由来）
npm run db:sql              # prisma/sql/**/*.sql を適用（scripts/apply-sql.ts）
```

`npm run db:setup` はこの2つをまとめて実行する。詳細・命名ルールは [`prisma/sql/README.md`](../prisma/sql/README.md)。

`DB.md` の §6（RPC設計）・§7（RLS方針）に書かれている関数・ポリシーは、実装時にここへSQLとして書き起こす。

## 4. Server Actions / server/ を書くときの型

書き込み（mutation）は`actions.ts`経由、読み取り（RSCから）は`server/`を直接。§1.1a参照。

```ts
// features/<domain>/server/some-server-fn.ts
import "server-only";
import { withRlsContext } from "@/lib/db/rls";

export async function someServerFn(userId: string, input: Parsed) {
  return withRlsContext(userId, async (tx) => {
    // ここでクエリ or PostgreSQL Function呼び出し
  });
}
```

書き込み（mutation）:

```ts
// features/<domain>/actions.ts
"use server";

export async function someAction(input: RawInput) {
  const userId = await getCurrentUserId();       // 1. 認証確認
  if (!userId) throw new Error("ログインが必要です");

  const parsed = someSchema.parse(input);          // 2. 入力バリデーション（zod）

  return someServerFn(userId, parsed);              // 3. server/ に委譲するだけ
}
```

読み取り（RSCから直接。actions.tsは経由しない）:

```tsx
// features/<domain>/components/some-component.tsx
import { getCurrentUserId } from "@/lib/supabase/server";
import { someServerFn } from "@/features/<domain>/server/some-server-fn";

export async function SomeComponent({ ... }) {
  const userId = await getCurrentUserId();        // 1. 認証確認（このコンポーネント自身が行う）
  if (!userId) return <p>ログインが必要です</p>;

  const data = await someServerFn(userId, ...);    // 2. server/ を直接呼ぶ
  return <>{/* ... */}</>;
}
```

実例: [`features/wallet/server/get-balance.ts`](../features/wallet/server/get-balance.ts) / [`features/wallet/components/wallet-balance.tsx`](../features/wallet/components/wallet-balance.tsx)（読み取りのみのドメインのためactions.tsが無い。書き込みが増えたら`features/groups/actions.ts`のようにactions.tsを追加する）。新しいドメインの実装はこの形を真似ることから始める。
