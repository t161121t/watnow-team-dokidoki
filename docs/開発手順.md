# 開発手順

この文書は、環境構築後に行うフロントエンドとバックエンドの技術的な開発手順をまとめたものです。初回セットアップは[環境構築手順](./環境構築手順.md)を参照してください。

コマンドは、特に記載がない限りリポジトリのルートで実行します。

## 1. 共通の準備

依存関係が未導入、または`pnpm-lock.yaml`が更新されている場合は、固定された依存関係をインストールします。

```bash
pnpm install --frozen-lockfile
```

固定されたツールのバージョンとDocker互換ランタイムの起動状態を確認するときは、次を実行します。

```bash
pnpm env:check
```

依存関係はpnpmだけで管理します。`.env.local`、キー、トークンなどの秘密情報はソースコードへ書かず、共有もしません。

## 2. フロントエンドの開発フロー

### 2.1 実装場所を決める

| 対象 | 主な場所 |
| --- | --- |
| 画面・ルーティング | `src/routes/` |
| 再利用するUI | `src/components/` |
| Supabaseクライアント・共通処理 | `src/lib/` |
| スタイル | `src/styles.css` |
| テスト | 対象に対応する`*.test.ts` / `*.test.tsx` |
| Supabase生成型 | `src/types/database.generated.ts` |

- ルートはTanStack Routerのファイルベース構成に従い、`src/routes/`へ追加します。
- `src/routeTree.gen.ts`は自動生成されるため、直接編集しません。
- サーバーデータはTanStack Query、フォームはReact Hook FormとZod、UI部品は既存のshadcn/ui構成を使用します。
- Supabaseへアクセスするときは`src/lib/supabase.ts`と生成済みの`Database`型を使用します。
- PWAのService Workerには、秘密本文や認証付きAPIレスポンスをキャッシュしません。

shadcn/uiのコンポーネントを追加するときは、固定されたコマンドを使います。

```bash
pnpm ui:add <component>
```

### 2.2 ローカルで確認する

画面を確認するときは、必要な環境変数を`.env.local`へ設定して開発サーバーを起動します。

```bash
pnpm dev
```

Supabaseを利用する画面では、後述のローカルSupabaseも起動します。

### 2.3 テストと検査を行う

変更した画面や処理に対応するVitest・Testing Libraryのテストを追加または更新します。

```bash
pnpm test
```

テストを監視しながら開発するときは、次を使用します。

```bash
pnpm test:watch
```

フロントエンドの実装がまとまったら、一括検査を行います。

```bash
pnpm verify:web
```

`pnpm verify:web`は、TypeScript型チェック、Vitest、本番ビルドなどを順番に実行します。

## 3. バックエンドの開発フロー

このプロジェクトのバックエンドはSupabaseです。複数テーブルの整合が必要な処理はPostgreSQL Function、外部HTTPやStorageとの連携はEdge Functionsに実装します。

### 3.1 ローカルSupabaseを起動する

Docker互換ランタイムを起動した後、ローカルSupabaseを起動して状態を確認します。

```bash
pnpm supabase:start
pnpm supabase:status
```

ローカルURLとPublishable keyの設定方法は[環境構築手順](./環境構築手順.md)を参照してください。

### 3.2 DB・RLS・PostgreSQL Functionを変更する

1. migrationファイルを作成します。

```bash
pnpm exec supabase migration new <migration-name>
```

2. 生成された`supabase/migrations/`配下のSQLへ、テーブル、RLS、PostgreSQL Functionなどの変更を記述します。
3. グループに属するテーブルにはRLSを設定します。重要なPostgreSQL Functionでも、呼び出しユーザーと`group_id`の所属関係を確認します。
4. 必要な初期データがある場合は`supabase/seed.sql`を更新します。
5. ローカルDBをmigrationとseedから再構築します。

```bash
pnpm supabase:reset
```

`pnpm supabase:reset`を実行するとローカルデータは失われます。

6. DBのTypeScript型を更新します。

```bash
pnpm supabase:types
```

7. `supabase/tests/database/`へpgTAPテストを追加または更新し、DB検査を実行します。

```bash
pnpm verify:db
```

### 3.3 Edge Functionsを変更する

- 実装は`supabase/functions/<function-name>/`へ置きます。
- テストは`supabase/functions/tests/`へ置きます。
- 新しいFunctionを追加した場合は、`supabase/config.toml`のFunction設定と、`supabase/deno.json`のworkspace・検査対象を更新します。
- 認証が必要なFunctionでは、設定と実装の両方で未認証リクエストを拒否し、そのテストを追加します。

実装後はEdge Functionsの一括検査を行います。

```bash
pnpm verify:edge
```

### 3.4 ローカルSupabaseを停止する

作業終了後、不要になったローカルSupabaseを停止します。

```bash
pnpm supabase:stop
```

## 4. 全体を確認する

フロントエンドとバックエンドをまとめて確認するときは、ローカルSupabaseを起動した状態で次を実行します。

```bash
pnpm verify
```

`pnpm verify`は、フロントエンド、Edge Functions、DBの検査を順番に実行します。
