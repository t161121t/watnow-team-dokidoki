## 1. ビジネスロジックの配置方針（確定）

**原則：複数テーブルにまたがる整合性が必要な処理はPostgreSQL Functionに、外部I/Oが絡む副作用処理はEdge Functionsに置く。**

| 処理 | 実装場所 | 理由 |
| --- | --- | --- |
| 入札処理（価格検証・行ロック・Wallet残高チェック・更新） | PostgreSQL Function | 同一トランザクション内で完結させ、レースコンディションを防ぐ |
| ポイントのcredit/debit | PostgreSQL Function | グループ完全分離の不変条件をSQLレベルで強制 |
| オークション終了確定処理 | PostgreSQL Function（`pg_cron`から定期実行） | 複数テーブルの一括更新をトランザクションで保証 |
| 複数人承認判定・ポイント付与 | PostgreSQL Function | 承認集計とポイント付与を同一トランザクションで実行 |
| プッシュ通知送信（落札・承認通知） | Edge Function | Web Push APIへの外部HTTPリクエストが必要 |
| 写真提出時のバリデーション・処理 | Edge Function | Storageとの連携、外部処理を伴う |

DBトリガーまたは`pg_cron`からEdge Functionを呼び出すことで、両者を連携させる。

## 2. 「グループ完全分離」の二重防御（確定方針）

1. **RLS**：`wallets`・`secrets`・`auctions`等の全テーブルに、所属グループのメンバーのみアクセス可能なポリシーを設定
2. **PostgreSQL Function内の明示チェック**：RPC関数の引数として受け取った`group_id`が、呼び出しユーザーの所属グループと一致するかを関数冒頭で必ず検証
3. **pgTAPによるポリシーテスト**：「他グループのWalletを読み書きしようとするとRLSで拒否される」ことを自動テストで担保

```sql
-- pgTAPテストの例（イメージ）
BEGIN;
SELECT plan(1);

-- 別グループのWalletへのUPDATEが拒否されることを確認
SELECT throws_ok(
  $$ UPDATE wallets SET balance = balance + 100
     WHERE group_id = 'other-group-id' $$,
  'new row violates row-level security policy'
);

SELECT * FROM finish();
ROLLBACK;
```

## 3. PWA構成（ネイティブアプリなし・確定）

- ホーム画面への追加を促すUI（初回起動時のインストールバナー）を実装
- iOS Safari 16.4以降のWeb Push制約（ホーム画面追加済みでないと通知不可）はユーザーに明示し、オンボーディング時に「ホーム画面に追加」を案内するフローを設ける
- Service WorkerはHTML・JavaScript・CSS等の静的アセットのみをキャッシュし、秘密本文や認証付きAPIレスポンスはキャッシュしない

---

## 4. 環境構築の完了条件

環境構築は次を満たした状態を完了とする。画面、業務ロジック、DBスキーマ、RLS、RPCの実装は含めない。

- Node.jsとpnpmのバージョンを固定し、lockfileから依存関係を再現できる
- Vite + React + TypeScriptの最小構成で開発用起動と本番ビルドができる
- Biome、TypeScript型チェック、Vitest、本番ビルドをpnpm scriptsから実行できる
- Tailwind CSS、shadcn/ui（Base UI）、TanStack Router / Query、React Hook Form、Zod、Supabase clientの初期設定がある
- Supabase CLIのローカル設定と型生成コマンドがある
- PWA manifestと静的アセット用Service Workerが設定され、秘密情報をキャッシュしない
- `.env.example`には変数名だけを記載し、秘密情報を含めない
- GitHub Actionsでinstall、Biome、型チェック、テスト、ビルドを検証できる
- Cloudflare Workers Static Assetsで`dist`をSPAとして配信する設定がある
