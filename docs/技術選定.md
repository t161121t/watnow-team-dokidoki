## 1. ビジネスロジックの配置方針（確定）

**原則：複数テーブルにまたがる整合性が必要な処理はPostgreSQL Functionに、外部I/Oが絡む副作用処理はEdge Functionsに置く。**

| 処理 | 実装場所 | 理由 |
| --- | --- | --- |
| 入札処理（価格検証・行ロック・Wallet残高チェック・更新） | PostgreSQL Function | 同一トランザクション内で完結させ、レースコンディションを防ぐ |
| ポイントのcredit/debit | PostgreSQL Function | グループ完全分離の不変条件をSQLレベルで強制 |
| オークション終了確定処理 | PostgreSQL Function（`pg_cron`から定期実行） | 複数テーブルの一括更新をトランザクションで保証 |
| 複数人承認判定・ポイント付与 | PostgreSQL Function | 承認集計とポイント付与を同一トランザクションで実行 |
| プッシュ通知送信（落札・承認通知） | Edge Function | Web Push APIへの外部HTTPリクエストが必要 |
| 写真提出時のバリデーション・処理 | Edge Function | Storageとの連携、外部処理を伴う |

DBトリガーまたは`pg_cron`からEdge Functionを呼び出すことで、両者を連携させる。

## 2. 「グループ完全分離」の二重防御（確定方針）

1. **RLS**：`wallets`・`secrets`・`auctions`等の全テーブルに、所属グループのメンバーのみアクセス可能なポリシーを設定
2. **PostgreSQL Function内の明示チェック**：RPC関数の引数として受け取った`group_id`が、呼び出しユーザーの所属グループと一致するかを関数冒頭で必ず検証
3. **pgTAPによるポリシーテスト**：「他グループのWalletを読み書きしようとするとRLSで拒否される」ことを自動テストで担保

```sql
-- pgTAPテストの例（イメージ）
BEGIN;
SELECT plan(1);

-- 別グループのWalletへのUPDATEが拒否されることを確認
SELECT throws_ok(
  $$ UPDATE wallets SET balance = balance + 100
     WHERE group_id = 'other-group-id' $$,
  'new row violates row-level security policy'
);

SELECT * FROM finish();
ROLLBACK;
```

### 4.1 Phase 2に回す理由（最初から導入しない理由）

| ツール | 最初から導入しない理由 |  |
| --- | --- | --- |
| **Playwright（E2E）** | E2Eテストは画面のDOM構造・操作フローに強く依存する。MVP段階は画面構成・UIフローそのものが頻繁に変わるため、先にE2Eを書くと画面変更のたびにテストを書き直すことになり、「テストのメンテナンスコスト」が「機能実装の速度」を上回ってしまう。UIがある程度落ち着いてから書く方が投資対効果が高い | 最後の仕上げ段階 |
| **Oxlint / Oxfmt** | Rust製で高速という利点はあるが、Vite+と同様にエコシステムとして比較的新しく、ルールセットや設定オプションがまだ変化している段階。MVP開発と並行してlintルールの調整に時間を取られるリスクがあるため、まずはESLint/Prettier相当の最小構成（もしくはNode標準）で開発速度を優先し、コードベースが固まってから高速なOxlint/Oxfmtへ移行する方が手戻りが少ない | 最初から、初期設定で問題ない |
| **pgTATの網羅的整備** | pgTAPによるRLSテスト自体は重要だが、「網羅的に」整備するにはテーブル設計が確定している必要がある。MVP期はテーブル・カラム構成がまだ変わりうるため、先に網羅的なテストを書くとスキーマ変更のたびにテストの書き直しが発生する。最初は「グループ完全分離」など致命的な不変条件のテストのみに絞り、スキーマが安定してから対象を広げる | 重要な部分だけ実装 |
| **Web Push本格運用** | VAPIDキー管理、購読（subscription）のライフサイクル管理、iOSのホーム画面追加要件への案内UIなど、通知まわりは実装量・検証項目（実機での動作確認を含む）が多い。MVPで検証すべきは「オークション・ポイントのコアゲームループが成立するか」であり、通知は無くてもコア体験の検証はできるため、後回しにしてもリスクが小さい | 最後に時間が余るなら |
| **Deno lint/fmt/check/testの厳格化** | Edge Functions自体の設計（どの処理をFunctionに切り出すか）がまだ固まりきっていない段階で厳格なlint/型チェックを敷くと、設計変更のたびに引っかかって開発速度が落ちる。まずは緩めの設定で試行錯誤し、Edge Functionsの責務が固まってから厳格化する方が合理的 | 厳格化まではいらない。 |

**共通する考え方**：これらはいずれも「対象（UI・スキーマ・Edge Functionsの設計）が変わりやすい段階で先に固めると、変更のたびに手戻りコストが発生する」種類のツールである。逆に言えば、コア機能（要件書1〜6章）が動く状態になり、対象が安定してから導入した方が、同じ投資でより長く効果が持続する。小規模チームでは「完成させること」が最優先事項であるため、変更耐性の低い投資は後回しにする。
