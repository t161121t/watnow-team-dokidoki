# ディレクトリ構成

## 基本方針

このリポジトリは、トップレベルの `src/` と `supabase/` を維持し、Frontend は小さな feature 単位で整理する。Clean Architecture や Feature-Sliced Design のような多層構造は導入せず、必要な実装が生まれた時点でだけディレクトリを増やす。

- `routes/` は URL と画面の接続に限定する
- 機能固有の実装は `features/` にまとめる
- 汎用 UI、アプリ共通 UI、基盤コードを分離する
- Frontend のテストは原則として対象実装の近くに置く
- Supabase は CLI の標準に近い構成を保つ
- 未実装機能の空ディレクトリや将来用の階層は先に作らない

## 責務

| 場所 | 置くもの | 置かないもの |
| --- | --- | --- |
| `src/features/<feature>/` | 機能固有の UI、Query、mutation、schema、hook、テスト | URL 定義、複数機能に共通する UI、汎用基盤 |
| `src/routes/` | URL、parameter、search parameter、guard、loader、feature との接続 | 大きな画面実装、業務ロジック、直接のデータ操作 |
| `src/components/ui/` | shadcn/ui など、業務知識を持たない UI プリミティブ | feature 固有の文言や状態遷移 |
| `src/components/` | 特定 feature に属さないアプリ共通 UI | 単一 feature だけで使う UI |
| `src/hooks/` | 複数 feature で実際に共有する汎用 React hook | feature 固有の hook |
| `src/lib/` | Supabase client、env、汎用 utility などの基盤 | 入札、ポイント、グループなどの業務ロジック |
| `src/types/` | 自動生成型など、アプリ全体で共有する型 | 単一 feature 内だけで使う型 |
| `src/test/` | Testing Library などの全テスト共通セットアップ | 個別機能のテスト本体 |
| `supabase/migrations/` | テーブル、RLS、PostgreSQL Function、trigger など | 外部 HTTP や Storage を扱う実行コード |
| `supabase/functions/` | 外部 HTTP、Storage、通知などを扱う Edge Functions | DB 内でトランザクション完結すべき処理 |
| `supabase/functions/tests/` | Edge Functions の Deno テスト | Frontend の Vitest、DB の pgTAP |
| `supabase/tests/database/` | DB、RLS、PostgreSQL Function の pgTAP テスト | Edge Functions のテスト |
| `supabase/seed.sql` | ローカル開発用の再現可能な初期データ | 本番用の秘密情報や手動運用データ |
| `docs/` | 仕様、技術方針、画面、ユーザーフロー、開発手順 | 実行時に読み込む設定やコード |

## Frontend の依存方向

```text
main.tsx
  ├── router.tsx ──> routeTree.gen.ts ──> routes/ ──> features/
  └── components/（アプリ全体の UI）

features/
  ├── components/ui/
  ├── components/
  ├── hooks/（存在する場合）
  ├── lib/
  └── types/
```

`features/` から `routes/` は import しない。`lib/` に feature 固有の都合を持ち込まず、共通化は二つ以上の利用箇所が実際に生まれてから行う。

## feature 内部の育て方

実装開始時は、関連ファイルを feature 直下へ平坦に置く。

```text
features/
└── auctions/
    ├── auction-card.tsx
    ├── auction-card.test.tsx
    ├── queries.ts
    ├── mutations.ts
    └── schemas.ts
```

UI ファイルが増え、一覧性が下がった段階でだけ `components/` などへ分割する。

```text
features/
└── auctions/
    ├── components/
    │   ├── auction-card.tsx
    │   ├── auction-list.tsx
    │   └── bid-form.tsx
    ├── queries.ts
    ├── mutations.ts
    └── schemas.ts
```

feature 固有の hook は feature 内に置く。同じ hook を複数 feature で共有する必要が生じた場合だけ `src/hooks/` へ移す。

## 配置の判断順

1. URL や navigation にだけ関係するか → `src/routes/`
2. 一つの機能にだけ関係するか → `src/features/<feature>/`
3. 複数機能で共有するアプリ UI か → `src/components/`
4. 業務知識を持たない純粋な UI か → `src/components/ui/`
5. Frontend 全体の基盤か → `src/lib/`
6. 複数テーブルの整合性を伴う DB 処理か → `supabase/migrations/` の PostgreSQL Function
7. 外部 HTTP、Storage、通知などの副作用か → `supabase/functions/`

ポイント、秘密、オークションのグループ完全分離はディレクトリ分割だけに頼らず、RLS と PostgreSQL Function 内のチェック、および pgTAP テストで保証する。
