# アーキテクチャ比較: Next.js + Prisma vs Vite + Supabase直結

ステータス: **確定（案A: Next.js + Prisma を維持）**。理由は §6
作成日: 2026-08-17

## 0. 背景

`chore/setup-DB` / `feat/app-architecture` で Next.js（App Router）+ Prisma を採用し、`docs/アーキテクチャ.md` として設計した。これに対しチームメンバーから「Vite（静的配信）+ Supabase Client 直結」の方が今回の要件には合うのではという意見が出た。これは `技術選定.md` が元々確定していた案（Vite + TanStack Router + Supabase完結型）への回帰でもある。

本ドキュメントは両案の意見・メリット/デメリットを中立に整理した上で、リーダー判断により **案A（Next.js + Prisma）を維持** することに決定した（§6）。

---

## 1. 2案の概要

### 案A: Next.js + Prisma（現状の実装）

- フロント/バックエンドとも Next.js（App Router）。データアクセスは Server Actions → `features/*/server/*` → Prisma Client（`lib/db/rls.ts` の `withRlsContext` でRLSを再現）
- Auth・Storage・Realtime は Supabase Client（`lib/supabase/server.ts`）
- マイグレーションは Prisma Migrate。RLSポリシー・PostgreSQL Functionsは `prisma/sql/`
- 詳細: [`docs/アーキテクチャ.md`](./アーキテクチャ.md)

### 案B: Vite + Supabase直結

- フロントは Vite の静的SPA。Cloudflare Pages 等に静的配信
- データアクセスはブラウザから Supabase Client で直接 `.from()` / `.rpc()`（RLSはSupabase標準のJWT+ポリシーがそのまま効く）
- 型は Supabase TypeGen（`supabase gen types typescript`）
- マイグレーションは Supabase CLI
- `技術選定.md` の元々の確定案に近い

## 2. 論点別比較

| 論点 | 案A: Next.js + Prisma | 案B: Vite + Supabase直結 | 評価 |
| --- | --- | --- | --- |
| 危険なロジック（入札・按分・残高）の安全性 | PostgreSQL Function（`prisma/sql/`）に実装 | PostgreSQL Function（Supabase CLI管理）に実装 | **ほぼ引き分け**。どちらも同じ関数に寄せる方針（AGENTS.md）なので、一番致命傷になりやすい処理の安全性は構成の選択でほとんど変わらない |
| 読み取り時のRLS保証 | `withRlsContext`（自作。トランザクション内で `SET LOCAL ROLE authenticated` + `set_config`）を経由しないとRLSが素通りする。ESLintで直接importを禁止しているが、仕組み自体は未検証（`docs/アーキテクチャ.md` §5） | Supabase Client のJWTがそのままRLSに使われる。追加の仕組み不要 | **案Bが単純で安全**。案Aは独自実装の分だけ、実装ミス・検証不足のリスクを負う |
| Realtime（価格・入札のリアルタイム反映） | Supabase Client直結（案Aでも変更なし） | Supabase Client直結 | **引き分け**。両案とも同じ実装になる |
| 通信段数・速度 | Browser → Next.js Server → Postgres | Browser → PostgREST/Supabase → Postgres | **ほぼ引き分け**。単純CRUDでのホップ数に大差はない |
| 型安全性の質 | Prisma Clientはクエリ形状（select・relation・filter）がスキーマに対し構造的に型検証される | Supabase TypeGenはテーブル/カラムの型は付くが、クエリビルダー自体の型検証はPrismaほど強くない | **案Aが有利** |
| マイグレーション体験 | `prisma migrate dev` でスキーマ変更→diff→適用が1コマンド。Prisma Studioで即データ確認可能 | Supabase CLIは基本手書きSQL。`supabase db diff` はあるがPrismaほど成熟していない | **案Aが有利**。DB.mdがまだ確定しきっていない現状では、スキーマ変更の摩擦の低さがハッカソンの速度に効く |
| サーバー運用 | Next.js Server（Vercel等）が必要。静的ホスティングよりは重い | Viteは静的配信のみで完結。Next.js Server自体が不要 | **案Bが有利** |
| Prisma特有の運用リスク | サーバーレス環境でのコネクションプール枯渇リスクがある（Supabaseのプーラー設定等の追加対応が必要） | 該当なし。PostgRESTが接続を内部で管理する | **案Bが有利**。案Aは「安全」なだけでなく、案Bにはない新種の運用リスクを持ち込む |
| Next.jsの強みの活用度 | SSR/SEOは今回の要件（ログイン後PWA・Realtime中心）では効かない。Server Actionsで秘密ロジック（DB接続情報等）をブラウザに渡さない点は独自の価値 | 該当なし（そもそもNext.jsを使わない） | **弱い差**。SSR/SEOでは案Aに強みはない。Server Actionsの隠蔽効果はあるが必須ではない |
| レイヤー数・実装/レビュー/障害調査コスト | レイヤーが多い（app → actions → server → withRlsContext → Prisma → Postgres） | レイヤーが少ない（browser → Supabase → Postgres） | **案Bが有利**。小規模・短期間のチームには効きやすい差 |
| チームの得意分野 | TypeScript/ORM的な書き方に慣れているなら書きやすい | SQL/RLSポリシーの記述に慣れているなら書きやすい | **未確認**。ここが実は一番効く変数かもしれない |

## 3. 双方の意見（原文ベース）

### 案B（Vite + Supabase直結）を推す意見

- Supabaseの機能（Auth / RLS / Realtime / Storage / PostgreSQL Functions）をそのまま使え、Next.jsのサーバー層を追加する必要がない
- 認可構成が単純。Supabase ClientのJWTをそのままRLSで使えるため、Prisma用の独自RLS処理が不要
- Realtimeが要件に合っている。入札・価格・状態変更を即時反映する必要があり、Browserから直接Supabase Realtimeへ接続できる
- 通信速度面でもNext.jsを挟む強いメリットがない。単純なDBアクセスでは通信段数はほぼ同じ。複雑な更新もPostgreSQL Functionにまとめれば通信回数を抑えられる
- Prismaの利点が小さい。Supabase TypeGenで型安全性を確保でき、複雑な更新もPostgreSQL Functionへ寄せるため、Prismaの強みを使う場面が少ない
- サーバー運用が不要。Viteは静的Frontendとして配信でき、Next.js ServerやPrismaのDB接続管理が不要
- 今回の要件ではNext.jsの強みが弱い。SEOやSSRが重要ではなく、ログイン後のPWA・Realtime中心のアプリ
- 小規模チームでは開発速度を上げやすい。レイヤーが少なく、実装・レビュー・障害調査の対象を減らせる

### 案A（Next.js + Prisma）を推す意見

- クエリの型検証がSupabase TypeGenより構造的に強く、按分・入札まわりの実装ミスをコンパイル時に検出しやすい
- Prisma Migrateはスキーマ変更→自動diff→適用が1コマンドで完結し、DB.mdがまだ確定しきっていない現状ではスキーマ変更の摩擦が小さい（Prisma Studioでのデータ確認も含む）
- 既にNext.js App Routerを選んでいる前提では、Server Actionsを使わない設計はフレームワークの標準機能を使わないことになり不自然。Server Actions経由にすることで、DB接続情報や按分ロジックがブラウザ側コードに一切現れない
- RLSに加えてアプリ層（`withRlsContext` + zodバリデーション）にもチェックポイントを持たせることで、RLSポリシー単体のミスがそのままデータ漏洩に直結する単一障害点を避けられる（ただしこの仕組み自体が自作で未検証というリスクも負う。§2参照）

## 4. 結論として言えること

- **一番致命傷になりやすい処理（入札・残高）の安全性は、案A/B どちらでもほぼ同じ**（両方ともPostgreSQL Functionに寄せるため）。「案Aの方が安全」という主張は、主に読み取り経路（RLSの保証範囲）に限った話であり、かつその保証自体（`withRlsContext`）が案Aでは自作かつ未検証
- 「サーバー運用」「レイヤー数」「Prisma特有の接続プール問題」は素直に案Bが有利
- 「型安全性の質」「マイグレーション体験」は素直に案Aが有利
- Realtime・通信速度は引き分け
- **技術的な優劣は僅差**。決定的な差にならない論点が多い

## 5. 決定に必要な情報（確認済み・2026-08-17）

- 残りの開発期間: **1週間未満**
- チームの得意分野: リーダー（意思決定・最終レビュー担当）が Next.js、もう1名が Vite。**1:1で拮抗**
- 案Aの実装（`chore/setup-DB` / `feat/app-architecture`）は既に `main` にマージ済み

## 6. 決定事項（2026-08-17）

**案A: Next.js + Prisma を維持する。**

理由:

1. 残り1週間未満で、案Aの実装（`chore/setup-DB` / `feat/app-architecture`、既に `main` にマージ済み）を破棄する余裕がない
2. 得意分野が1:1で拮抗しており、技術論だけでは決め手にならない。この場合は「最終レビュー・マージ判断を行うリーダーが速く正確に読めるスタック」を優先する（AGENTS.mdの「レビュー/マージ判断は人間」という役割分担に沿う）
3. §4で整理した通り、一番致命傷になりやすい処理（入札・残高）の安全性はどちらの案でもほぼ同じなので、この観点では案Bへ切り替える強い理由にならない

残る課題（フォローが必要）:

- Vite側に習熟したメンバーが Next.js / Prisma の書き方に不慣れな場合の立ち上がりコスト。`features/wallet/`（`docs/アーキテクチャ.md` §4）の実装パターンをそのまま真似てもらう形でオンボーディングコストを下げる
- `withRlsContext`（`lib/db/rls.ts`）はまだ実DBに対する動作検証をしていない。テーブルが1つでもマイグレーションされ次第、最優先でE2E確認する（`docs/アーキテクチャ.md` §5 に既出）
